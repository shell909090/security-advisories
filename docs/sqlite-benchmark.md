# SQLite 第一版性能对比

使用当前同内容的 state.json（24,866,846 字节）和 state.sqlite（18,690,048 字节），分别运行7次独立 Python 进程，交替执行两种后端，报告中位数。使用项目 .venv Python，不计 uv 启动耗时；计时包括 Python 启动、模块导入和退出。Linux ru_maxrss 记录整个子进程的峰值 RSS。输入文件复制到临时目录，不清空操作系统文件缓存，属于本机热缓存测试；未联网，不代表冷盘或完整在线 update 的性能。

摘要均使用 --all --min-severity high，避免读写展示历史。近三天采用默认窗口，全历史增加 --history，单产品选择当前配置首项 hermes。两种后端的摘要输出 SHA-256 一致。

| 场景 | JSON 耗时（秒） | SQLite 耗时（秒） | JSON 峰值 RSS（MiB） | SQLite 峰值 RSS（MiB） |
| --- | ---: | ---: | ---: | ---: |
| 全产品近三天 summary | 0.310 | 0.163 | 149.3 | 44.4 |
| 全产品全历史 summary | 0.376 | 0.226 | 149.4 | 44.4 |
| 单产品近三天 summary | 0.259 | 0.086 | 149.5 | 31.5 |
| update 存储阶段：仅加载（包含 HTTP 缓存） | 0.440 | 0.507 | 236.9 | 219.8 |
| update 存储阶段：加载后原样保存（包含 HTTP 缓存及 SQLite VACUUM） | 1.137 | 1.674 | 275.8 | 219.9 |

SQLite VACUUM 后副本为18,472,960字节，比原始 JSON 小25.7%。原文件未被基准修改。结果显示摘要受益于按产品读取 catalog；update 全量读取的 SQLite 节点查询/解码仍有开销，保存阶段还包括逐节点比较与全库 VACUUM，当前未做到比 JSON 更快。该基准没有执行网络采集、catalog 重建和新增/删除工作负载，不能将这里的 RSS 视为完整在线 update 峰值。
