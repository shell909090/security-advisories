# 需求

## 目标与范围

每天获取关注产品的新漏洞及重要更新，过滤后提供可行动的信息；看到问题再核对设备版本与配置，不要求预先采集安装版本。首批产品为 Hermes Agent、OpenCode、Claude Code、Codex CLI。

- 系统实际使用、由 Debian 更新的依赖默认交给系统维护，不重复做全包扫描。
- 项目自行管理、捆绑或静态编译的主要依赖应纳入关注，记录所属产品和依赖依据。不能因系统依赖包更新就认为静态副本已修复。
- 产品相关公告不等于本机可利用漏洞；依赖关系、影响范围不明时标为待核实。

## 采集与过滤

数据源包括 GHSA、OSV、NVD、CVE 官方记录及项目自己的安全公告。每个源独立实现统一接口，由主程序自动发现，并发抓取；新增源不应修改调度名单。

既检查新增，也检查已有公告的重要更新；支持分页、增量与重叠窗口。单源失败不推进进度、不冒充无漏洞，其他源仍可完成。

统一记录、合并 CVE/GHSA/OSV 别名后，依次过滤：

1. 严重性：默认仅 Critical，支持调整最低等级或跳过。
2. 产品：默认确认属于关注清单，支持跳过；不能仅凭描述中出现产品名判断命中。
3. 排重：默认使用持久历史，忽略无变化内容；支持指定历史文件或跳过。

默认报告近三天发布或更新的公告，以及已知条目的重要变化；历史梳理显式开启。未知严重性不混入 Critical，允许单列待复核；无 CVE 的有效 GHSA 仍可保留。不同来源评级冲突须保留并说明。

## 输出与日常循环

报告应提供产品、漏洞编号、严重性及评分来源、问题所在组件、触发条件与后果、修复和规避方法、变化原因及原始链接。缺少信息明确标注未知，不编造。

代码负责采集和确定性过滤；AI 后续辅助解读、核对和处置建议。新增问题和影响范围、修复办法等重要变化应再次报告，已通报不等于永久免除。

最终支持每日执行和通知：投递成功后记录已通知，失败可重试。完整报告临时生成，持久数据仅保留配置、必要缓存、同步进度和排重/投递状态，不保存全量漏洞数据库。

## 当前边界

已实现采集、过滤和 JSON 输出。AI 审核、每日调度、通知投递及投递确认尚未实现；主要自管依赖待确认后加入配置。当前摘要不是上述完整处置报告，输出历史也不代表通知成功。
