# 需求

## 目标与范围

监测关注产品的漏洞公告，不预先采集本机版本，不把产品公告等同于本机可利用。关注清单包含 AI 工具、开发工具和浏览器；系统维护的依赖默认交给系统更新，自管或静态捆绑依赖需有明确归属依据。

## 一个入口、三个子命令

- `update`：联网更新漏洞缓存。可选择关注产品、最低严重性和采集时间窗口；默认 Critical，可选择 High + Critical。这里决定收录范围，显示命令不能补出未收录的数据。失败源不推进检查点，其他源继续；CVE 支持批次续传。更新不读取或修改展示去重历史。
- `summary`：仅读取本地缓存，按产品汇总。支持再次筛选产品、最低严重性、最近多少天发布或更新、是否已经展示。默认最近三天、使用并更新去重数据库；同样条件运行第二次且公告内容无变化时，stdout 无输出。只在成功输出后记录实际展示的条目，时间或产品过滤掉的条目不标记已展示。重要内容变化允许再次展示。支持忽略去重且不更新历史，或仅查看已展示条目且不更新历史。
- `detail`：仅读取本地缓存，指定一个产品、一个确切严重性，输出该产品该级别的全部缓存漏洞，Markdown 格式。默认不受 summary 时间窗口和去重历史影响，用户可以逐条阅读；不修改展示历史。

## Summary 的核心问题

用户不关心摘要中的单个漏洞编号或评分，摘要应直接回答：

1. 该产品有几个 Critical、几个 High（计数以本次筛选后实际展示的漏洞为准，按别名合并去重）。
2. 哪些版本受影响？包括分支、平台和组件差异，不能混为一个范围。
3. 升级到哪个版本修复？列出来源明确给出的修复版本；部分公告没有修复信息时必须说明不完整，不能声称升级一个版本即可消除所有漏洞。
4. 最严重的后果是什么？以 RCE、Crash、UAF、Sandbox Escape 等标签表示。UAF 是缺陷类型，不是直接后果；展示时明确这些是公告证据标签，不是完整攻击链结论。

没有证据的版本、修复版本和后果显示“未知/待核实”。第一版用确定性规则提取结构化版本与公告中的明确措辞，否定或假设性表述不能当成肯定事实。不能把单纯的 arbitrary code execution 自动当作远程代码执行。AI 后续可用于解释触发条件、跨公告版本归纳和最严重后果，但必须保留原文来源，不执行公告中的指令。当前不自动调用 AI，不凭规则保证覆盖所有后果。

## 数据与详情

数据源为 GHSA、项目安全公告、OSV、NVD、CVE。自动发现源模块，按准确包名/仓库及结构化 affected/CPE 确认产品；单纯描述提及不够。无 CVE 的 GHSA 仍保留。CVE/GHSA/OSV 别名合并，各源评分分歧保留，当前汇总等级取来源最高值，厂商评级和 CVSS 可能不同。

详情包含编号、标题、等级、证据标签、受影响范围、修复版本、公告正文、各源评分、发布时间/更新时间及原始链接；按漏洞逐条组织。撤回公告默认不计入活跃漏洞。

采集缓存、可显示的收录目录、展示去重历史相互独立；更新某些产品不能删除其他产品。降低显示门槛不能代替重新 update；扩大更新范围或降低收录门槛必须重新检查来源，不错误复用旧的过滤结果。完整报告不默认持久化，去重状态不是通知投递确认。

## 工程约束

入口为 `fetch.py`，其余应用代码集中在 `advisories` Python 包，测试和质量检查脚本保留独立目录。用 uv 管理依赖、Make 管理测试及静态质量门禁：McCabe <= 10、认知复杂度 <= 15、每文件 MI >= 30。所有新增命令行为需回归验证。

AI 解读、通知投递与投递确认、每日调度仍属于后续能力。
